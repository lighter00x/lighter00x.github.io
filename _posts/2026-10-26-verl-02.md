第一次训练能启动后，我开始关心另外一个问题：任务现在忙在哪里？只看终端日志，很难判断资源使用和任务状态，于是我打开了 Ray Dashboard。

但 Metrics 页面提示：

```text
Time-series charts are hidden because either Prometheus or Grafana server is not detected.
```

这篇记录我在昇腾 ARM64 环境里补齐监控链路的过程。主要环境为 Ray 2.46.0，实验发生在 2026 年 7 月。

## 1. 先理解三个组件怎么配合

| 组件 | 在这套链路中的职责 |
| --- | --- |
| Ray Dashboard | 展示集群、任务和 Actor 状态，并嵌入指标图表 |
| Prometheus | 抓取 Ray 导出的指标并保存时间序列 |
| Grafana | 查询 Prometheus，绘制面板 |

Dashboard 能打开，只能说明 Dashboard 服务可访问。时序图还需要后面两个组件，以及正确的数据源和访问地址。

这和后续使用 W&B 记录 reward、KL、工具调用等训练指标是两个层面的事情：前者主要帮助观察运行系统，后者帮助理解实验行为和结果。

## 2. 检查现有环境

我先确认本机有没有安装对应程序：

```bash
which prometheus
which grafana-server
python -c "import ray; print(ray.__version__)"
uname -m
```

当时 Prometheus 和 Grafana 都没有安装，机器架构为 aarch64。下载二进制包时必须选 ARM64，不能直接使用常见的 amd64 包。

## 3. Prometheus 下载成功，却没有启动

当时使用：

```bash
ray metrics launch-prometheus
```

这条命令在我的环境中下载了 ARM64 的 Prometheus，但文件落在执行命令时的工作目录下，而不是自动加入 PATH。随后启动失败：

```text
listen tcp 0.0.0.0:9090: bind: address already in use
```

这说明下载与执行已经推进到监听端口的阶段，当前问题是 9090 被占用，而不是程序没有安装。

我尝试用常见网络工具查端口，但环境里的工具不可用或存在依赖问题，最后从 `/proc/net/tcp` 确认监听记录：

```bash
cat /proc/net/tcp | grep ':2382'
```

`2382` 是 9090 的十六进制表示。这里只能辅助确认 socket 记录，要定位进程还需要进一步关联 inode，不能直接把它当作完整的进程排查结果。

为了不影响共享机器上的现有服务，我把 Prometheus 改到 19090。

## 4. 无 sudo 权限也可以部署 Grafana

当时没有合适的管理员安装权限，我选择下载 ARM64 二进制包到用户目录。以下保留版本选择，路径写法经过整理：

```bash
cd /tmp
wget https://dl.grafana.com/oss/release/grafana-10.2.0.linux-arm64.tar.gz
tar -xzf grafana-10.2.0.linux-arm64.tar.gz
mv grafana-10.2.0 "$HOME/grafana"
mkdir -p "$HOME/grafana-data"
```

安装后检查 Ray 生成的 Grafana 配置：

```bash
ls /tmp/ray/session_latest/metrics/grafana/
```

当时能看到 `grafana.ini`、`provisioning` 和 `dashboards`。这些文件把 Grafana 数据源和 Ray 的面板连接起来，启动时应使用对应配置。

Grafana 默认的 3000 端口也被占用，我改成了 13000。在我的环境中，用 `GF_SERVER_HTTP_PORT` 覆盖端口更直接；这是一种明确的配置方式，不需要把它解释成环境变量普遍比命令行参数可靠。

## 5. 真正容易忽略的是启动顺序

Ray Dashboard 需要知道 Prometheus 和 Grafana 的地址。因此相关变量必须在启动 Ray 时就进入它的进程环境，不能在启动完成后仅在另一个 shell 中 export。

我当时使用的端口是：

| 服务 | 端口 |
| --- | ---: |
| Ray Dashboard | 8265 |
| Ray metrics export | 8080 |
| Prometheus | 19090 |
| Grafana | 13000 |

下面是整理后的启动片段。`MASTER_IP` 需替换成服务器地址，Prometheus 的路径需指向实际解压目录。

```bash
export MASTER_IP=10.154.24.54
export RAY_PROMETHEUS_HOST="http://${MASTER_IP}:19090"
export RAY_GRAFANA_HOST="http://${MASTER_IP}:13000"
export GF_SERVER_HTTP_PORT=13000
export GF_PATHS_DATA="$HOME/grafana-data"
export PROMETHEUS_BIN=/实际解压目录/prometheus
```

如果浏览器访问 Grafana 的地址与 Ray 服务端使用的地址不同，需要额外配置 `RAY_GRAFANA_IFRAME_HOST` 为浏览器可达地址。服务端健康检查和浏览器加载面板是两条访问路径。[Ray 的 Grafana 接入说明](https://docs.ray.io/en/latest/cluster/kubernetes/k8s-ecosystem/prometheus-grafana.html)

先启动自己管理的 Ray 实验实例。下面沿用第一篇的历史资源声明，新部署时应按当前 NPU 适配逻辑核对：

```bash
ASCEND_RT_VISIBLE_DEVICES=0,1,2,3 ray start --head \
  --num-cpus 32 \
  --num-gpus 4 \
  --resources='{"NPU":4}' \
  --dashboard-host=0.0.0.0 \
  --dashboard-port=8265 \
  --metrics-export-port=8080
```

再启动 Prometheus 和 Grafana：

```bash
nohup "$PROMETHEUS_BIN" \
  --config.file /tmp/ray/session_latest/metrics/prometheus/prometheus.yml \
  --web.listen-address=:19090 \
  > /tmp/prometheus.log 2>&1 &

nohup "$HOME/grafana/bin/grafana-server" \
  --config /tmp/ray/session_latest/metrics/grafana/grafana.ini \
  --homepath "$HOME/grafana" \
  > /tmp/grafana.log 2>&1 &
```

相较原始笔记，这里去掉了 Grafana 命令末尾多余的 `web` 参数，并通过 `GF_PATHS_DATA` 指定数据目录，避免把 `~` 放在参数赋值内部时产生路径展开歧义。这是整理后的命令，尚未在远端重新执行。

还有一个实际细节：`session_latest` 会随着 Ray 重启指向新的 session。Ray 重建后，应确认监控配置仍然对应当前 session，必要时重启监控服务。

## 6. 验证时把“服务存活”和“有数据”分开

可以先检查服务状态：

```bash
curl -fsS http://127.0.0.1:19090/-/ready
curl -fsS http://127.0.0.1:13000/api/health
```

接着检查 Prometheus targets 是否正常抓取 Ray，以及 Grafana 的 Prometheus 数据源是否可用。最后回到 Ray Metrics 页面，看图表是否加载、是否存在当前时间范围的数据。

如果服务接口成功但图表仍为空，可以顺着这条路径查：Ray 有没有导出指标，Prometheus 有没有抓到，Grafana 有没有查到，浏览器能不能加载面板。健康检查成功并不能替代后面几步。

## 7. 监控接通以后，能看到什么

这套链路让我能更方便地观察节点状态、CPU 和内存、任务执行及部分 Ray 指标。但它不会自动生成所有强化学习曲线，也不代表已经完整采集昇腾 NPU 的利用率、HBM 和温度。

我后面把观测分成三部分：Ray 看任务与集群，`npu-smi` 等设备工具看 NPU，W&B 看 reward、KL、响应长度和工具行为。把这些信息放在一起，才更容易解释训练为什么变慢、为什么失败，以及模型有没有进步。
