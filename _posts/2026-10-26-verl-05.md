单机 NPU 实验完成后，我开始尝试 NVIDIA 多机环境。手头有三台服务器，每台 6 张 RTX 3090，共 18 张卡。我想先把环境、共享存储、Ray 调度和跨机通信串起来，为后续多机训练建立基础。

这篇基于当时的部署记录整理。现有材料包含集群截图、GPU 任务执行输出和通信测试代码，但没有完整的多机训练配置及最终验证日志。因此本文重点放在搭建与验证，不把集群在线直接等同于完整训练复现。

## 1. 先给三台机器固定角色

下面沿用实验内网地址，仅用于说明当时的拓扑，复现时替换成自己的地址。

| 节点 | 地址 | GPU | 角色 |
| --- | --- | --- | --- |
| head | `10.154.24.41` | 6 × RTX 3090 | Ray head、NFS server |
| worker1 | `10.154.24.42` | 6 × RTX 3090 | Ray worker、NFS client |
| worker2 | `10.154.24.43` | 6 × RTX 3090 | Ray worker、NFS client |

当时记录的驱动版本是 575.64.03，`nvidia-smi` 显示 CUDA Version 12.9。这个字段反映驱动支持的 CUDA 能力，不能据此认定容器实际安装或 PyTorch 使用的 runtime 就是 12.9。

检查时我主要看：

```bash
nvidia-smi --query-gpu=index,name,uuid --format=csv
ip addr show
docker info
```

进入容器以后，还需要检查 `torch.__version__`、`torch.version.cuda` 和 `torch.cuda.device_count()`。宿主机看到 6 张卡，并不意味着容器配置已经完成。

## 2. 统一镜像，也统一代码

当时使用的镜像标签是：

```text
docker.1panel.live/verlai/verl:vllm017.latest
```

这只是历史镜像来源和标签，不保证今后仍可下载。带 `latest` 的标签可能变化，长期复现还应记录镜像 digest。

为了减少重复下载，我先在一台机器拉取，再通过局域网传输镜像。下面修正了原笔记里压缩包保存路径与 scp 路径不一致的问题：

```bash
# 在已有镜像的节点执行
docker save -o /tmp/verl_vllm017.tar docker.1panel.live/verlai/verl:vllm017.latest
gzip /tmp/verl_vllm017.tar
scp /tmp/verl_vllm017.tar.gz xq@10.154.24.43:/tmp/

# 在接收节点执行
gunzip -c /tmp/verl_vllm017.tar.gz | docker load
```

原始 Compose 在每次启动时执行 `git pull`。这样操作方便，却容易让三台机器的代码发生漂移。整理后更建议将安装与服务启动分开：先让三台机器使用同一个 commit，再启动 Ray。

```bash
git rev-parse HEAD
python -c "import torch, ray, verl; print(torch.__version__); print(ray.__version__); print(verl.__file__)"
```

同一个版本字符串仍可能对应不同开发提交，记录 commit 比只记录 `verl.__version__` 更可靠。

## 3. SSH 用来运维，NFS 用来共享数据

我当时配置了节点间 SSH，方便传文件和执行命令。这里需要区分：SSH 免密不是 Ray Worker 加入集群或 NCCL 通信的必需条件，它是部署方式的一部分。

配置密钥时先检查已有密钥，不要照抄笔记中覆盖 `id_rsa` 的交互过程。覆盖已有密钥可能影响其他登录关系。

共享数据采用 NFS。head 上的目录是：

```text
/mnt/sda_8t/share/data_xq/data_verl
```

两个 worker 挂载到：

```text
/mnt/sdb_2_4t/data_xq
```

原始记录中 NFS server 的注释一度写成 42，但实际导出与挂载关系指向 41。这里统一按 41 作为 server。

在 worker 节点上，整理后的挂载命令为：

```bash
sudo apt install -y nfs-common
sudo mkdir -p /mnt/sdb_2_4t/data_xq
sudo mount -t nfs \
  10.154.24.41:/mnt/sda_8t/share/data_xq/data_verl \
  /mnt/sdb_2_4t/data_xq
mount | grep /mnt/sdb_2_4t/data_xq
```

这修正了原记录里创建目录与挂载点不同，以及 `mkdir -p ls ...` 的笔误。以上是手动挂载方式，重启后的持久化挂载需要另行配置。

server 的导出范围限定为两个 worker。原环境使用过 `no_root_squash`；它会影响客户端 root 身份的权限映射，是否保留应结合容器写入和用户权限设计决定。

## 4. 让容器内看到相同的路径

三台宿主机的物理路径可以不同，但容器内统一映射为：

```text
/workspace/data
/workspace/code
```

head 把本地共享目录映射到 `/workspace/data`，worker 把 NFS 挂载目录映射到同一个位置。这样训练配置里的模型、数据和输出路径才能在各节点上指向同一份内容。

下面是整理后的公共 Compose 骨架，主要展示路径和运行条件。`.env` 中设置各节点自己的 `DATA_DIR` 与 `CODE_DIR`：

```yaml
services:
  verl:
    image: docker.1panel.live/verlai/verl:vllm017.latest
    network_mode: host
    ipc: host
    ulimits:
      memlock: -1
      stack: 67108864
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
    volumes:
      - ${DATA_DIR}:/workspace/data
      - ${CODE_DIR}:/workspace/code
    environment:
      NCCL_SOCKET_IFNAME: ens5f0
      NCCL_IB_DISABLE: "1"
      NCCL_DEBUG: WARN
      CUDA_VISIBLE_DEVICES: "0,1,2,3,4,5"
      PYTHONUNBUFFERED: "1"
      HF_HOME: /workspace/data/models/hf_cache
    command: ["sleep", "infinity"]
```

head 的 `DATA_DIR` 是导出目录，worker 的 `DATA_DIR` 是 NFS 挂载目录。每台机器还要设置真实的本地代码目录，并确认 NVIDIA Container Toolkit 可用。

这里保留 `network_mode: host` 与 `ipc: host`，因为它们简化了本次实验的网络和共享内存配置；不能把它们写成所有 NCCL 部署都必须满足的条件。`ens5f0` 也是当时实际使用的网卡名，其他环境必须重新确认。

原笔记中的 `NCCL_TIMEOUT=1800` 没有在本文中继续作为超时保证。超时应检查实际通信库及框架接口是否支持对应设置，不能因为 export 了变量，就认定它已经生效。

## 5. Ray 集群：所有 worker 指向同一个 head

容器内先安装同一份固定版本的代码及匹配依赖，再启动 Ray。下面假定已有可用容器环境，Compose 服务名为 `verl`。

head 上执行：

```bash
docker compose exec verl ray start --head \
  --node-ip-address=10.154.24.41 \
  --port=6379 \
  --num-gpus=6 \
  --dashboard-host=0.0.0.0 \
  --dashboard-port=8265
```

两个 worker 分别执行，`NODE_IP` 改成各自地址：

```bash
NODE_IP=10.154.24.42
docker compose exec verl ray start \
  --address=10.154.24.41:6379 \
  --node-ip-address="$NODE_IP" \
  --num-gpus=6
```

原始 Compose 中虽然设置了 head 为 41，但 worker 的连接命令却指向了 42。这是配置内部的不一致，整理后统一指向 `10.154.24.41:6379`。

启动后在容器内运行 `ray status`，并打开 Dashboard，确认三个节点和预期资源。注册了 18 个 GPU 资源，还需要继续验证任务执行和通信。

## 6. GPU 任务执行成功，能证明到哪一步

原记录提交了 18 个 `num_gpus=1` 的 Ray task，各自执行 CUDA 矩阵运算并返回结果。这支持“Ray 能分配 GPU 资源，任务能完成 CUDA 计算”。

但短任务可能复用同一张卡；原始输出中两台 worker 的 hostname 还相同，仅凭 hostname 和 18 行输出，不能严格证明 18 张物理卡各被使用了一次。

另外，Ray 会限制 Worker 的设备可见性。进程内打印的 `GPU 0` 可能是该进程看到的局部编号，不代表所有任务都落在宿主机物理 0 号卡。

下面补充一个整理后的验证示例：用持续占用资源的 Actor，检查节点 ID 和 Ray 分配的设备 ID。它没有在本次整理中实际运行。

```python
import os
import ray

ray.init(address="auto")

@ray.remote(num_cpus=1, num_gpus=1)
class GPUProbe:
    def inspect(self):
        import torch
        ctx = ray.get_runtime_context()
        x = torch.ones(8, device="cuda")
        return {
            "node_id": str(ctx.get_node_id()),
            "gpu_ids": ctx.get_accelerator_ids().get("GPU", []),
            "visible_devices": os.environ.get("CUDA_VISIBLE_DEVICES"),
            "device_name": torch.cuda.get_device_name(0),
            "sum": x.sum().item(),
        }

actors = [GPUProbe.remote() for _ in range(18)]
try:
    results = ray.get([actor.inspect.remote() for actor in actors], timeout=180)
    for item in results:
        print(item)
    assignments = {
        (item["node_id"], tuple(item["gpu_ids"])) for item in results
    }
    assert len(assignments) == 18, assignments
    assert all(item["sum"] == 8 for item in results)
finally:
    for actor in actors:
        ray.kill(actor)
    ray.shutdown()
```

这个检查假定集群有 18 张空闲、完整 GPU 资源和足够 CPU。如果有其他任务占用资源，应调整数量或先核对集群状态，不能把等待资源直接当成设备故障。

## 7. NCCL 测试：所有 rank 必须一起参与

原始测试代码先做 `all_reduce` 和 `all_gather`，随后在 `if rank == 0` 分支内重复调用 `all_reduce` 做计时，而其他 rank 进入了 barrier。

这会造成集体通信调用不匹配。默认进程组中的 collective 需要组内所有 rank 以一致顺序参与；可以只让 rank 0 打印，但不能只让它通信。[PyTorch 分布式通信文档](https://docs.pytorch.org/docs/stable/distributed.html)

下面是纠正后的检查示例，尚未在远端重新运行：

```python
import os
import time
from datetime import timedelta

import torch
import torch.distributed as dist

def main():
    local_rank = int(os.environ["LOCAL_RANK"])
    torch.cuda.set_device(local_rank)
    device = torch.device("cuda", local_rank)
    dist.init_process_group("nccl", timeout=timedelta(minutes=5))
    try:
        rank = dist.get_rank()
        world_size = dist.get_world_size()

        value = torch.tensor([rank], dtype=torch.float32, device=device)
        dist.all_reduce(value)
        expected = world_size * (world_size - 1) / 2
        assert value.item() == expected, (rank, value.item(), expected)

        local = torch.tensor([rank], dtype=torch.int64, device=device)
        gathered = [torch.empty_like(local) for _ in range(world_size)]
        dist.all_gather(gathered, local)
        assert [t.item() for t in gathered] == list(range(world_size))

        # 所有 rank 按同样顺序执行；仅 rank 0 输出结果。
        # 使用零张量，避免重复求和导致数值快速放大。
        payload = torch.zeros(1024 * 1024, device=device)
        for _ in range(3):
            dist.all_reduce(payload)
        dist.barrier()
        torch.cuda.synchronize()
        start = time.perf_counter()
        for _ in range(10):
            dist.all_reduce(payload)
        torch.cuda.synchronize()
        elapsed = torch.tensor(
            [time.perf_counter() - start], dtype=torch.float64, device=device
        )
        dist.all_reduce(elapsed, op=dist.ReduceOp.MAX)
        if rank == 0:
            print(f"world_size={world_size}, correctness checks passed")
            print(f"10 all-reduces: slowest rank {elapsed.item():.3f}s")
        dist.barrier()
    finally:
        dist.destroy_process_group()

if __name__ == "__main__":
    main()
```

将相同脚本保存到三台机器的容器内。三个节点都启动下面的命令；可先在 head 上启动，再在另外两台启动：

```bash
torchrun \
  --nnodes=3 \
  --nproc_per_node=6 \
  --rdzv_backend=c10d \
  --rdzv_endpoint=10.154.24.41:29500 \
  --rdzv_id=verl-nccl-check-01 \
  test_nccl.py
```

18 个 rank 的求和期望值为 153。这个小规模脚本用来检查正确性和粗略耗时，不把张量大小除以耗时直接当作真实网络带宽；带宽比较还需要更规范的测试条件。

## 9. 多机实践给我的提醒

多机问题经常出在边界：三台机器是否导入同一份代码，容器内路径是否一致，worker 是否连对 head，通信是否走对网卡，各 rank 是否执行了相同的 collective。

我现在会按“单卡计算 → 集群资源 → 跨节点任务 → 集体通信 → 短程训练 → 保存与恢复”的顺序推进。这样每一步都有明确证据，也更容易区分调度问题、通信问题和训练问题。
