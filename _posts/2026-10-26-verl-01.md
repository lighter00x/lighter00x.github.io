刚开始接触 verl 时，我给自己定的目标很具体：先让一个小模型在昇腾服务器上完成训练，再逐步理解背后的执行链路。真正动手之后才发现，环境能导入、NPU 能被识别，以及训练能跑起来，是三件不同的事。

这篇记录我在 2026 年 7 月搭建环境和排错的过程。模型选择 Qwen3-0.6B，数据集使用 GSM8K，训练算法使用 GRPO。这里的命令对应当时的环境；整理时补充的检查方法会单独说明。

## 1. 先把环境记清楚

服务器共有 8 张 Ascend 910B4-1，每张 HBM 为 64 GB。实际首次训练只使用其中 4 张卡。

| 项目 | 当时的配置 |
| --- | --- |
| NPU | 8 × Ascend 910B4-1，单卡 64 GB |
| 宿主机驱动 | 25.2.2 |
| 宿主机 CANN | 8.2.RC2 |
| 容器镜像标签 | `verl-8.2.rc1-910b-ubuntu22.04-py3.11-latest` |
| 容器内 PyTorch | 排错时检查为 2.5.1 |
| 首次训练使用设备 | 4 张 NPU |
| 最终采用的训练策略 | FSDP |

需要区分宿主机与容器：宿主机的 CANN 版本，不代表容器内的工具包版本。镜像标签也不能代替完整依赖清单。当时为了尽量少改动共享服务器，我选择了现有环境附近的镜像组合；这是一条实际跑通过的路径，不能据此推导所有相邻版本都兼容。

## 2. 用容器把环境固定下来

当时拉取的镜像是：

```bash
docker pull swr.ap-southeast-1.myhuaweicloud.com/base_image/ascend-ci/verl/verl:verl-8.2.rc1-910b-ubuntu22.04-py3.11-latest
```

我用 Docker Compose 启动容器。下面保留当时的主要配置：

```yaml
services:
  verl_910b:
    image: swr.ap-southeast-1.myhuaweicloud.com/base_image/ascend-ci/verl/verl:verl-8.2.rc1-910b-ubuntu22.04-py3.11-latest
    container_name: verl_910b
    privileged: true
    ipc: host
    network_mode: host
    command: /bin/bash
    volumes:
      - /usr/local/Ascend/driver:/usr/local/Ascend/driver
      - /usr/local/Ascend/firmware:/usr/local/Ascend/firmware
      - /usr/local/dcmi:/usr/local/dcmi
      - /usr/local/bin/npu-smi:/usr/local/bin/npu-smi
      - /usr/local/sbin:/usr/local/sbin
      - /usr/sbin:/usr/sbin
      - /home/xq/projects:/workspace
    tty: true
    stdin_open: true
```

这份配置采用了较宽的设备权限和目录挂载，是当时实验环境的记录。关键是确认容器能访问宿主机驱动，并把代码、模型和实验产物放进持久化目录。重新部署时应按所用镜像的说明选择挂载项。

```bash
docker compose up -d
docker exec -it verl_910b /bin/bash
```

容器中已有 verl、vLLM、vLLM-Ascend、Megatron-LM 和 MindSpeed 等目录。我没有从零重新安装全部组件，而是先检查现成环境是否可用。

## 3. 环境检查要分层进行

在我的容器里，环境脚本位于：

```bash
source /usr/local/Ascend/ascend-toolkit/set_env.sh
source /usr/local/Ascend/nnal/atb/set_env.sh
npu-smi info
```

然后检查 Python 层：

```python
import torch
import torch_npu
import verl
import vllm

print("torch:", torch.__version__)
print("torch_npu:", torch_npu.__version__)
print("NPU count:", torch_npu.npu.device_count())
print("NPU 0:", torch_npu.npu.get_device_name(0))
print("verl:", verl.__file__)
print("vllm:", vllm.__file__)
```

这些检查分别回答：驱动能否识别卡、Python 能否访问 NPU、当前导入的库来自哪里。它们通过后，还要继续验证模型初始化、rollout、反向更新和 checkpoint，才能确认训练链路可用。

## 4. 准备模型和 GSM8K 数据

模型通过 ModelScope 下载。下面是整理后的写法，用返回值确认最终目录，避免依赖缓存布局：

```python
from modelscope import snapshot_download

model_path = snapshot_download(
    "Qwen/Qwen3-0.6B",
    cache_dir="/workspace/models",
)
print(model_path)
```

我当时踩的第一个坑就是模型路径。脚本希望拿到一个可以直接读取 `config.json`、tokenizer 和权重的目录，而我最初传的是缓存上层目录。实际缓存还套着 `snapshots/master` 等层级，结果模型下载了，训练仍然找不到配置。

![当时记录的模型缓存目录层级](/images/verl/image-20260723173709792.png)

解决思路很简单：把 `MODEL_PATH` 指向真正包含模型文件的目录，不要靠修改 `MODEL_ID` 拼出缓存路径。

GSM8K 也需要经过预处理，转换成训练脚本需要的 prompt 和奖励字段。当时的记录里，`--local_dataset_path` 的用法没有成功，最终使用：

```bash
python3 examples/data_preprocess/gsm8k.py \
  --local_save_path /workspace/data/gsm8k
```

这里的参数名以当时 checkout 的脚本为准。换版本时先执行 `--help`，并检查脚本究竟是在线读取原始数据，还是接受本地数据输入。

准备完成后，把训练脚本中的模型和数据路径一起核对：

```bash
MODEL_PATH=/workspace/models/实际模型目录
TRAIN_FILE=/workspace/data/gsm8k/train.parquet
TEST_FILE=/workspace/data/gsm8k/test.parquet
```

这三个变量只是路径配置片段，需要放进原训练脚本中使用。

## 5. 第一个关键问题：卡能看到，Worker 却拿不到 NPU

最初选择的是官方 quick start 中的 `run_qwen3_0_6b_fsdp2_vllm_ascend.sh`。运行到 Worker 初始化时，出现：

```text
local_rank = ray.get_runtime_context().get_accelerator_ids()[device_name][0]
IndexError: list index out of range
```

检查 `ray status` 后，我看到 Ray 同时注册了 GPU 和 NPU 资源。继续沿着 Worker 创建逻辑追踪，发现当时配置中的 `trainer.device` 仍走 CUDA 路径：Worker 申请的是 GPU slot，之后却尝试读取 NPU ID，自然得到了空列表。

当时的修复是在训练参数中显式添加：

```bash
trainer.device=npu
```

这次排查让我意识到，硬件探测和调度资源申请必须保持一致。不能因为 `torch_npu` 能导入，就认为训练配置也已经自动切换到 NPU。

## 6. 第二个关键问题：物理卡号与进程内索引混在一起

共享服务器上最初空闲的是物理卡 1、2、3、4。我设置了：

```bash
export ASCEND_RT_VISIBLE_DEVICES=1,2,3,4
```

随后遇到 `invalid device=4`。排查记录显示，Ray 返回的 NPU ID 中有 `4`，而下游设备选择逻辑没有正确协调可见设备列表与进程内索引。

当时我没有继续修改设备映射代码，而是在协调释放 0 号卡后，改用物理卡 0、1、2、3，绕过了这个问题。

整理时需要修正一个过强的结论：**这不代表 NPU 训练普遍要求物理卡从 0 连续编号。** Ray 官方文档本身给出了非连续设备可见性的例子；我的问题发生在当时的 Ray、verl、torch_npu 和环境变量组合中。换环境时，应同时打印 Ray accelerator IDs、Worker 的可见设备变量和设备数量，再定位映射发生在哪一层。[Ray 加速器资源说明](https://docs.ray.io/en/latest/ray-core/scheduling/accelerators.html)

## 7. 第三个关键问题：当前环境的 FSDP2 路径不兼容

设备问题处理后，又遇到：

```text
AttributeError: 'function' object has no attribute 'FSDPModule'
```

报错位置在 verl 的 FSDP 适配逻辑，涉及 `fully_shard_module.FSDPModule`。当时检查到 PyTorch 为 2.5.1，最终把训练策略从 `fsdp2` 改成了：

```bash
actor_rollout_ref.actor.strategy=fsdp
```

这里更准确的结论是：当时这套代码与 PyTorch 组合的 FSDP2 导入或适配路径不匹配，切到 FSDP 后解决了眼前问题。仅凭这条异常，不能把所有 FSDP2 功能的支持边界简单归结为一个版本号。

## 8. 最终保留下来的配置经验

当时记录的 Ray 启动命令如下，仅适用于自己管理的实验 Ray 实例，重启前需要确认没有其他任务依赖它：

```bash
ray stop
ASCEND_RT_VISIBLE_DEVICES=0,1,2,3 ray start --head \
  --num-cpus 32 \
  --num-gpus 4 \
  --resources='{"NPU":4}'
```

其中同时声明 GPU 和 NPU 是历史工作配置，不应当成所有 NPU 环境的标准模板。新环境应先确认 Worker 实际申请的资源类型，再设置对应资源，避免虚假的 GPU 声明掩盖问题。

训练侧的关键片段是：

```bash
export ASCEND_RT_VISIBLE_DEVICES=0,1,2,3
export RAY_EXPERIMENTAL_NOSET_ASCEND_RT_VISIBLE_DEVICES=1
export HCCL_CONNECT_TIMEOUT=1500
export HCCL_HOST_SOCKET_PORT_RANGE=60000-60050
export HCCL_NPU_SOCKET_PORT_RANGE=61000-61050
```

再配合 `trainer.device=npu`、4 卡配置和 FSDP 策略。禁用 Ray 自动修改可见设备变量的设置，也出现在 verl 的 NPU FAQ 中；是否启用仍要结合当前设备管理逻辑判断。[verl NPU FAQ](https://verl.readthedocs.io/en/latest/ascend_tutorial/en/faq/faq.html)

这篇整理的是路径、设备和训练策略等关键改动，并非完整训练脚本。实际复现仍需要对应版本的 quick start、模型和预处理后的数据。

## 9. 第一次跑通之后，我学到了什么

这次实践最大的变化，是我开始按执行层次排查问题：先看驱动和容器，再看 Python 依赖，接着看 Ray 资源，最后看 Worker 和训练引擎。

错误往往显示在链路后端，原因却在上游配置。沿着调用关系找到资源从哪里申请、设备号在哪里变化，比反复叠加环境变量更有效。
