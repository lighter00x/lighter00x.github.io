在跑通 GSM8K 的小模型训练后，我开始尝试更接近 Agent 的任务：让模型在回答问题时调用搜索工具，并通过强化学习改进整个过程。

这次选择的是 SearchAgent-Zero。最初我做了一份静态迁移分析，随后完成了 Qwen3-4B 在 4 张昇腾 NPU 上的搜索训练。本篇把前期判断和后期实际结果串起来，重点解释迁移要处理哪些边界。

## 1. 从数学回答到多轮搜索

数学问答中的 rollout，可以先理解为模型根据 prompt 生成回答，再由奖励函数打分。搜索 Agent 在这个过程中多了一层交互：模型生成工具请求，执行器调用检索服务，把结果交回模型，模型再决定继续搜索还是回答。

从训练视角看，一条轨迹里可能包含推理文本、工具调用、检索返回和最终答案。训练系统需要处理的不只是文本生成，还包括协议解析、轮次控制、工具异常、不同片段的训练处理和最终奖励。

这也是我选择基于现成 Agent 框架实践的原因：先把完整链路跑通，再理解每个模块的作用。

## 2. 前期分析：哪些变化值得关注

2026 年 7 月 24 日的记录中，我比较了两个本地代码目录：

| 项目 | 当时记录的版本 |
| --- | --- |
| 原版 verl | `0.9.0.dev` |
| SearchAgent-Zero | `0.8.0.dev` |

它们的差异涉及数百个文件。但两个目录本身就存在版本差异，因此不能把所有 diff 都归因于搜索 Agent 功能，也不能仅凭版本字符串建立精确的上下游关系。

我重点关注了以下模块：

| 模块 | 阅读目的 |
| --- | --- |
| `verl/tools/search_tool.py` | 搜索请求如何发出、如何限流和重试 |
| `verl/experimental/agent_loop/tool_agent_loop_credit_assignment.py` | 多轮交互、工具执行和轨迹组织 |
| `examples/search_agent_rl/` | 示例配置、数据处理和检索服务入口 |
| `verl/trainer/main_ppo.py` 与 PPO 相关代码 | 设备配置、训练入口和算法调用 |
| `verl/utils/device.py` | CUDA/NPU 检测及设备抽象差异 |
| rollout 与 Worker 配置 | 训练、推理和权重同步如何衔接 |

原始评估还列举了扩散模型、异步训练、视觉工具等模块。它们有助于了解仓库范围，但不能都算作当前 Search-R1 任务的必需迁移项。

## 3. 没有新增 CUDA kernel，不等于迁移已经完成

初步阅读时，搜索工具和 Agent 控制逻辑主要使用 Python、Ray、HTTP 请求及 PyTorch，没有在这些模块里识别出必须移植的新 CUDA kernel。这说明工具编排层有复用空间。

但我最初写下的“新增代码没有 CUDA 依赖”“复制约 15 个文件即可”都过于绝对。单看 import 列表，不能证明运行路径没有设备假设；把文件复制过去，也不能保证配置类、调用接口和训练逻辑匹配。

整理后，我把迁移拆成四个实际问题：

1. 训练端能否在 NPU 上执行前向、反向和优化器更新？
2. rollout 引擎能否在 NPU 上完成所需的多轮生成？
3. Agent loop 能否正确执行工具协议、组织返回内容并计算奖励？
4. 训练后的权重能否同步回 rollout 引擎，继续下一步采样？

只有四个环节连起来，才算完成训练迁移。自动检测到 NPU，只解决了其中很小一部分。

## 4. 最终采用的部署边界

实际实验中，我采用了分开部署的方式：

| 部分 | 部署位置 | 作用 |
| --- | --- | --- |
| Qwen3-4B 策略训练与 rollout | 昇腾服务器，使用 NPU 0、1、2、3 | 生成轨迹、计算训练所需概率、更新策略 |
| 检索服务 | NVIDIA 服务器，提供 HTTP 接口 | 接收搜索请求并返回检索结果 |
| W&B | 自托管服务及本地 run 目录 | 保存配置和训练指标 |

工具侧通过 HTTP 使用检索服务，因此训练设备和检索设备可以分开选择。

这里也修正了早期报告的一处判断：不能把检索服务统一称为“纯 CPU 服务”。HTTP 接口不依赖训练端使用 CUDA 还是 NPU，但检索内部的编码器、索引和搜索实现仍可能使用 GPU。后期记录明确采用了远端 NVIDIA 检索服务。

这种拆分让我可以先复用现有检索基础设施，集中处理 NPU 训练和 rollout 的兼容问题，而不必同时迁移所有组件。

## 5. 配置迁移时，我重点核对什么

### 设备和训练后端

第一篇已经记录过，Ray 资源类型、`trainer.device`、Worker 可见设备和设备索引必须一致。进入搜索任务后，这些基础条件依然适用。

最终实验的 checkpoint 元数据记录为 FSDP version 1、world size 4。这里可以确认实际保存下来的策略采用了 4 卡 FSDP 分片。

### rollout 和工具协议

前期方案曾考虑 vLLM-Ascend 和 SGLang-Ascend。整理现有材料时，没有把某一个候选方案直接写成最终后端；最终选择应以该 run 的完整 `config.yaml` 和启动脚本为准。

比后端名称更需要关注的是：当前版本能否执行对应 Agent loop、模型输出能否被工具 parser 接受、搜索结果是否进入下一轮上下文，以及轮次和长度限制是否按预期生效。

### 奖励函数

不能看到配置或日志里有某个分数，就认定它参与了优化。后续实验产物记录的关系是：

```text
score = origin_score + format_score
```

`efficiency_score` 被记录为诊断指标，没有加到总奖励中。这个事实会直接影响结果解释。

## 6. 用小规模实验验证完整链路

最终完成的实验名为 `qwen3-4b-search-r1-npu-1day`。名称里的 “1day” 是当时的实验命名，实际运行约 7 小时 8 分钟。

| 项目 | 实际记录 |
| --- | --- |
| 模型 | Qwen3-4B |
| 训练数据 | 4096 条 |
| 验证数据 | 固定 700 条 |
| train batch | 256 |
| 每个 prompt 的 rollout 数 | 5 |
| epoch | 2 |
| 总 step | 32 |
| prompt / response 上限 | 4096 / 3000 token |
| Agent worker | 8 |

这里有两组容易混淆的数量：Agent worker 是工具交互执行侧的并发配置，不等于 NPU 数；每个 prompt 的 5 条 rollout 是同一问题的采样轨迹，也不等于 5 个训练 step。

在本次整除的数据配置下：

```text
4096 / 256 = 16 step / epoch
16 × 2 = 32 step
256 × 5 = 1280 条轨迹 / step
1280 × 32 = 40,960 条轨迹
```

## 7. 我用哪些产物判断它确实跑完了

后期实验记录给出了以下完成证据：

- 训练完成 32/32 step，并执行最终验证。
- 保存了 step 8、16、24、32 的 checkpoint，按保留策略留下最近两份 actor。
- 生成了 32 个 rollout JSONL，共 40,960 条轨迹。
- W&B run 状态为 `finished`，有训练前验证和 32 个训练 step 的 history。
- 记录中的日志异常检查未发现 OOM、`RayTaskError`、`RuntimeError` 或 traceback。

这些信息共同支持“NPU 训练、远端检索、奖励计算、策略更新及产物保存已经连通”。仅有一个服务在线或一张设备利用率截图，还不足以得到同样的结论。

## 8. 这次迁移留下的认识

迁移搜索 Agent 的难点，是让训练引擎、生成引擎、工具执行和奖励计算遵循同一套配置与协议。设备适配是基础，但要以完整的一步训练和最终产物作为验证终点。

现有学习记录没有包含最终兼容补丁清单，也缺少早期文档引用的完整迁移 runbook。因此这篇保留架构、检查顺序和实际跑通的配置规模，没有虚构一套“复制这些文件就能复现”的安装命令。
