把搜索 Agent 的训练跑起来，只完成了实践的一半。接下来我需要回答：模型有没有改善？改善来自答得更对，还是只学会了格式？训练变慢有没有合理原因？保存下来的文件又能做什么？

这篇基于 2026 年 7 月 25 日至 26 日完成的 `qwen3-4b-search-r1-npu-1day` 实验记录整理。文中的数字来自当时的实验分析文档，本次整理没有重新访问远端日志或重算原始轨迹。

## 1. 先说最重要的结果

在同一份固定 700 条验证子集上，训练后的正确性奖励和格式奖励都高于初始模型：

| 指标 | 初始 | 最终 | 绝对变化 |
| --- | ---: | ---: | ---: |
| 总 reward / score | 0.089143 | 0.416286 | +0.327143 |
| `origin_score` | 0.085714 | 0.321429 | +0.235714 |
| `format_score` | 0.003429 | 0.094857 | +0.091429 |
| `efficiency_score`，诊断项 | 0.254286 | 0.475000 | +0.220714 |

这里可以说，当前模型与工具系统在这份验证子集上的表现改善了。`origin_score` 的具体定义仍取决于奖励实现，不能不经核对就把它直接写成标准准确率，也不能把总 reward 当作准确率。

## 2. 实验究竟用了什么设置

| 项目 | 配置 |
| --- | --- |
| 模型 | Qwen3-4B |
| 训练设备 | 4 张昇腾 910B NPU |
| 检索 | 远端 NVIDIA 服务器上的检索服务 |
| 训练 / 验证规模 | 4096 / 700 |
| train batch / rollout 数 | 256 / 5 |
| prompt / response 最大长度 | 4096 / 3000 token |
| PPO mini batch / 每卡 micro batch | 128 / 1 |
| epoch / step | 2 / 32 |
| 实际耗时 | 约 7 小时 8 分 |
| W&B run ID | `8thx8izw` |

训练集由 HotpotQA 2184 条和 NQ 1912 条组成。验证集包含七个来源：除 Bamboogle 为 28 条外，其余每个来源都是 112 条。

数据记录使用 seed 42，并通过 `subset_manifest.json` 保存来源、数量和 SHA-256。固定这些信息的意义在于，后续比较模型时，能确认评估输入确实相同。

W&B 的 33 行 history 也有明确来源：训练前验证 1 行，加上训练 step 1 至 32，不是重复写了一个训练 step。

## 3. 看曲线之前，先核对奖励组成

原始分析记录对全部 40,960 条轨迹做过校验，得到：

```text
score = origin_score + format_score
不一致记录数 = 0
```

所以本次训练的总分由正确性和格式两部分组成，`efficiency_score` 只是记录下来的诊断值。不能把三个分数直接相加，也不能因为效率分提高，就声称训练直接优化了效率。

这个区别很容易被忽略：日志字段告诉我们“记录了什么”，奖励实现才告诉我们“实际优化了什么”。

## 4. 训练确实改善了，但后期进入波动

为了减少单个 batch 的随机性，原始分析比较了前 8 step 和后 8 step 的均值：

| 指标 | 前 8 step | 后 8 step |
| --- | ---: | ---: |
| 总 reward | 0.237715 | 0.539717 |
| `origin_score` | 0.209375 | 0.442676 |
| `format_score` | 0.028340 | 0.097041 |
| `efficiency_score` | 0.306006 | 0.486426 |
| entropy | 0.072221 | 0.049481 |
| grad norm | 0.860866 | 0.430925 |
| actor KL loss | 0.021288 | 0.105060 |
| 平均响应长度 | 587.31 token | 839.08 token |
| 平均工具调用数 | 0.8845 | 1.2784 |
| 平均 step 时间 | 748.17 秒 | 816.73 秒 |

正确性分的提升是总 reward 上升的主要来源，格式分也接近其 0.1 上限。从这里看，模型既适应了输出协议，也在答案评价上获得了更高分。

但 reward 没有单调增加：

| step | 训练 reward |
| --- | ---: |
| 1 | 0.136250 |
| 16 | 0.512969 |
| 24 | 0.565156 |
| 29 | 0.581641，训练曲线最大值 |
| 32 | 0.509609 |

不同 step 使用的训练 batch 和采样轨迹不同。step 29 的训练 reward 最高，不代表它在固定验证集上最好；最终 step 下降，也不能单凭这一点认定模型退化。更合适的解释是：前中期明显改善，后期在较高水平波动。

## 5. KL、entropy 和梯度要放在一起看

后期 entropy 降低、actor KL 增加，和策略逐渐偏离 reference、输出分布更集中这一解释相符。梯度范数没有同步爆炸，原始记录也没有发现 NaN、Inf 或训练崩溃。

这支持“本次短程实验没有观察到明显数值失稳”，但不足以证明继续训练很长时间仍会稳定。

另外，`actor/kl_loss` 与 `rollout_corr/kl` 比较的对象不同。前者与 reference 正则相关，后者用于观察 rollout 和训练侧概率差异。不能只比较两个数值的大小，就判断两个引擎是否一致；还需要结合计算定义和概率检查结果。

## 6. 为什么后期更慢了

后 8 step 的平均回答从约 587 token 增长到 839 token，平均工具调用从约 0.88 次增长到 1.28 次，step 时间也从约 748 秒增长到 817 秒。

回答变长、交互变多，与训练耗时上升是相容的解释：更多 token 会增加生成、概率计算和更新的工作量，更多工具交互也可能增加等待。

不过仅凭这些均值，还不能精确拆分每个因素的耗时贡献。进一步定位应看 `timing_s/gen`、`old_log_prob`、`ref`、`update_actor` 和 `update_weights` 等阶段指标。

本次工具调用成功率指标在训练各 step 均为 1.0，parser error 大部分为 0。但成功发出并返回工具调用，不等于检索内容相关，也不等于模型正确利用了证据。这部分需要回看轨迹。

## 7. 验证集按来源拆开看

| 数据源 | 初始 reward | 最终 reward |
| --- | ---: | ---: |
| 2WikiMultihopQA | 0.029464 | 0.374107 |
| Bamboogle | 0.071429 | 0.492857 |
| HotpotQA | 0.093750 | 0.480357 |
| Musique | 0.049107 | 0.341071 |
| NQ | 0.066071 | 0.375000 |
| PopQA | 0.018750 | 0.283929 |
| TriviaQA | 0.282143 | 0.624107 |

七个来源的 reward 都提高了，其中也包括训练来源之外的数据集。这是积极的观察，但尚不能替代数据去重、完整 benchmark 和多随机种子评估。

总体 reward 必须按样本数加权：

```text
总体均值 = Σ(每个来源样本数 × 该来源均值) / 700
```

Bamboogle 只有 28 条，不能与 112 条的组直接等权平均；它的变化也更容易受少量样本影响。

## 8. 训练结束后，checkpoint 里有什么

本次每 8 step 保存一次，actor 最多保留最近两份：

| step | dataloader 状态 `data.pt` | actor 权重 |
| --- | --- | --- |
| 8、16 | 保留 | 已按策略删除 |
| 24、32 | 保留 | 保留 |

step 24 和 32 的 actor 目录各约 47 GB，包含 4 个 rank 的模型分片、优化器分片和额外恢复状态。checkpoint 比最终推理权重大很多，与保存了优化器等训练状态有关。

几个文件的用途要分清：

- `data.pt` 保存数据加载恢复状态，不能独立作为模型使用。
- `model_world_size_4_rank_*.pt` 是模型分片。
- `optim_world_size_4_rank_*.pt` 是优化器分片。
- `extra_state_world_size_4_rank_*.pt` 保存额外训练状态。
- `actor/huggingface/` 在本次产物中只有模型配置、tokenizer 和模板，没有合并后的权重。

因此，直接把 `actor/huggingface/` 交给推理引擎，并不能加载这次训练得到的模型。

原记录给出了以下合并方式，使用前应在对应 checkout 中核对 CLI 参数：

```bash
cd /workspace/SearchAgent-Zero
python -m verl.model_merger merge \
  --backend fsdp \
  --local_dir output/qwen3-4b-search-r1-npu-1day/global_step_32/actor \
  --target_dir output/qwen3-4b-search-r1-npu-1day/global_step_32/merged_huggingface
```

合并完成后需要检查权重文件，并实际加载模型、运行生成。只调用 `AutoConfig` 和 `AutoTokenizer`，只能验证元数据，不能验证权重完整性。现有记录也没有提供合并与推理成功的日志，因此这里把它作为后续步骤。

## 9. rollout 比一张 reward 曲线更具体

这次共生成 32 个 JSONL，每个文件 1280 条，共 40,960 条轨迹，约 196 MB。每条记录包含输入、输出、参考答案、step 和奖励分项。

所有训练轨迹的总分均值为 0.431316。这个数字混合了早期与后期策略，不能代替最终模型在验证集上的表现。

我更关心的轨迹问题是：模型是否重复搜索？高分是否来自正确答案？回答变长以后增加的是证据推理，还是冗余文本？格式分很高的失败样本长什么样？同一问题的 5 条轨迹差异有多大？

这些问题能帮助决定下一次实验该改奖励、数据、长度限制，还是工具配置。

## 10. 保留什么，才能让实验以后还能解释

原始实验记录中的主要产物包括：数据约 9.1 MB、训练日志约 7.9 MB、checkpoint 约 93 GB、rollout 约 196 MB、本地 W&B run 约 1.7 MB。

其中完整配置、数据 manifest、日志、最终模型和轨迹，构成了后续复盘的基础。W&B summary 通常保存最后一次写入值，例如本次最终训练 reward 为 0.509609；寻找曲线最大值和趋势仍需要 history。

恢复训练也要看完整 checkpoint 和原配置。已经完成 32/32 后，再执行原脚本不等于自动开启一个有意义的新实验；延长训练需要重新设计训练步数和评估方式。

这次实验最扎实的结论是：搜索训练链路在当前部署上完整运行，最终模型在固定验证子集上的评分优于初始模型。下一步值得做的是补充独立评估、轨迹审查和候选 checkpoint 比较，再决定如何扩大训练规模。
